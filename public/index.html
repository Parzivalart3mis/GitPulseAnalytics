What it does

Repository data is rich. Querying it shouldn't require writing SQL.

GitPulseAnalytics collects issues, pull requests, commits, and repository metadata from the GitHub API into PostgreSQL — then puts a natural-language layer on top of it.

Instead of hand-writing a join across four tables and a plotting script every time a question comes up, you type the question. The system generates schema-aware Python that connects to the database, loads the relevant tables into pandas, and renders the answer as text, a table, or a chart in a Streamlit app.

It also handles forecasting: Prophet for issue volume, ARIMA/SARIMA for commits and pull requests, projected 30 days out.

Key features

Built like a pipeline, not a prompt box

Every query runs through generation, static analysis, LLM review, and sandboxed execution before you see a result.

Natural-language queries

Ask in English. The writer agent is primed with the full database schema, so it produces valid joins and column references instead of hallucinated ones.

Two-layer code review

Deterministic static checks (AST compile, banned file I/O, import correctness) run alongside an LLM reviewer that returns a 0–100 quality score and an accept/reject verdict.

Charts and tables on demand

matplotlib, seaborn, and plotly outputs render straight into the Streamlit surface. Charts are generated only when the question actually asks for one.

Time-series forecasting

Prophet models issue trends; statsmodels ARIMA/SARIMA handles commit and PR velocity. Per-repository fits are aligned on a shared time index for clean comparison.

Normalised Postgres store

A collection notebook pulls repos, issues, pulls, and commits via PyGithub into four typed tables — so analysis runs against a real relational store, not raw API responses.

Transparent by default

The generated code, the review score, and the execution result are all shown in the UI. Nothing runs behind a curtain — you can read exactly what was executed.

The multi-agent workflow

One question, four stages

The orchestrator coordinates three specialised agents, each with a single responsibility.

01

Query intake main.py · Streamlit

You type an analytics question into the Streamlit interface. The orchestrator takes it from there — there are no dropdowns, filters, or pre-built dashboards to configure.

02

Writer agent writer_agent.py

A GPT-4o-mini call through LangChain receives the question plus the full schema of all four tables. It returns executable Python — Postgres connection, pandas loading, analysis, and Streamlit rendering — with markdown fences stripped by the orchestrator.

Temperature is held at 0.1 to keep generated code deterministic across repeat runs.
03

Reviewer agent reviewer_agent.py

Two checks run in sequence. Static analysis compiles the code and flags concrete violations — plt.show() calls, file I/O, input(), missing imports, wrong Prophet usage, or a timestamp column that contradicts the question. Then an LLM reviewer scores quality 0–100 and returns ACCEPTED or REJECTED.

Static findings cap the score at 70, and anything below 50 is forced to REJECTED — so the deterministic checks always outrank the model's opinion.
04

Executor agent executor_agent.py

The approved code runs in a LangChain PythonREPL, with execution errors caught and surfaced rather than crashing the app. The generated code, quality score, and result — text, dataframe, or figure — are returned together to the UI.

The review runs before execution and is reported alongside the output; the current build surfaces the score rather than using it as a hard gate.
Data model

Four tables, one schema contract

The same schema is embedded in the writer agent's prompt and enforced by the reviewer's static checks.

TableContentsKey columns
github_repos Repository-level popularity metrics repo · stars · forks
github_issues Issue lifecycle and labelling state · created_at · closed_at · labels
github_pulls Pull request flow and authorship state · merged_at · user_login
github_commits Commit history per contributor sha · author_login · committed_at
